# SE Blank、只读诊断和持久化 root

## 为什么先进入 SE Blank

最初需要在触摸不能操作、固件版本尚不明确的条件下取得可靠诊断入口。后来从设备文件确认版本为 5.16.2.1.1。旧越狱教程或其他机型成功案例不足以证明 KT3 兼容。

这里的名称是 **SE Blank / Freescale SDP**，不是“se bland”。它是 USB 下载/恢复入口；进入该模式本身不等于 root 或已经写入固件。

## 短接点核对

依据 [KT3 原始讨论和图片](https://www.mobileread.com/forums/showthread.php?t=327055)，现场照片按屏幕连接器、旁边电容列、屏蔽罩、斜置空焊盘等地标对应两个点：原图标为 **+3V** 与 **USB BOOT**。

**TP1706 / TM401 在本次 KT3 板上没有独立通断或丝印确认。** [Popcorn 总教程](https://www.mobileread.com/forums/showthread.php?t=345655)对部分其他机型直接使用这些标号，而 KT3 指向单独教程。不能把其他板的标号机械套到本板。

现场成功操作的核心条件：

1. 先按对应板型原图确认两个点，使用板内信号短接，不注入外部电压，不把电源直接短到地。
2. 在短接保持期间让设备复位，USB 数据线连接电脑；复位时间参照对应板型教程，不能用某个按键秒数代替 USB 枚举检查。
3. 电脑确认出现 Freescale SDP 设备。本机曾观察到 **VID 15A2 / PID 0063**。
4. 枚举成功后移开短接，保留 USB，才加载已核对的 KT3 RAM 诊断环境。

电子纸会保留断电前图像，屏幕不变不能证明没有进恢复模式。公开仓库不附会暴露设备标识的整板照片，也不提供未核对板型可照抄的通用焊盘图。

## RAM 诊断阶段的迭代

| 现象 | 判断与处理 |
|---|---|
| 内存上传完成，但没有 USB 网络 | 上传成功不代表内核、init、USB gadget 或 SSH 已成功 |
| RNDIS 被 Windows 识别成 COM 设备 | 按实际接口和网络设备类核对绑定，不向任意串口强装网卡驱动 |
| 只有诊断日志盘，没有 SSH | 利用只读日志回传定位初始化和 `/dev` 挂载错误 |
| USB 网卡重枚举后主机地址丢失 | 只恢复专用 USB 网卡地址，不改 Wi-Fi、网关或 DNS |
| RAM root 可用 | 确认实际 uid=0、设备挂载状态、主机密钥和命令返回，再考虑持久化 |

临时环境把必要的可写状态放在 RAM，并只读挂载原文件系统。早期镜像的初始化顺序和 devtmpfs 问题均经过失败—日志—修复循环；没有把“下载完成”写成“root 成功”。

## 备份与密钥核查

先保存 eMMC 用户区完整镜像、boot0、boot1、关键原始文件及 SHA256 清单。备份只在私有工作目录保存；**RPMB 不在本次备份范围**，因此不能称为芯片所有区域的完整克隆。

核查原 `uks.sqsh` 在持久化安装前后保持不变。SSH 使用设备专属密钥及主机指纹，禁止复制这台设备的私钥或配对资料给其他设备。原始日志可能含设备身份，因此公开日志为重写的脱敏摘要。

## 持久化实现与回滚

正常启动下新增 `/opt/kt3-root` 和 `/etc/upstart/kt3-root.conf`，提供自定义 USB 公钥 SSH。正常重启后验证原内核、原 init 和 uid=0，根分区恢复只读。这是项目自定义的 USB SSH 持久化，不等同于 OTA 保活越狱，也不等同于安装 KUAL。

能 SSH 时，先审查本机安装时保存的 `/opt/kt3-root/rollback.sh`，复制到临时目录再执行，保留密钥与备份直到验证原系统启动。不能 SSH 时，重新进入 SE Blank，以匹配本机的 RAM 诊断环境恢复访问，再使用本机备份撤销改动。

**不要使用他人的完整 eMMC 镜像恢复本机**；不要在未确认分区、只读保护和校验结果时运行写盘命令。本仓库故意不提供可误用的通用 dd 写盘脚本。
