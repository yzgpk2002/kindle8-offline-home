# KT3 连续立体声版本：2026-11-06

当前默认基线为 `continuous-state3`。用户要求恢复此前无重连提示版本后，已从设备备份原样恢复，并实听确认“有声音，没有重连提示”。这不是长期稳定性认证：此前连续多次切歌仍曾出现卡顿并发展为无声。

## 版本与范围

代码快照在 [releases/2026-11-06-continuous-state3](../releases/2026-11-06-continuous-state3/README.md)。目标为已经完成本项目改造的 KT3，与既有手动主页、原生蓝牙及 GStreamer mixersink 配合。仅保存此次关键服务/播放器，不是完整固件、独立安装包或通用 Kindle 补丁。旧 `src` 仍是早期参考源码，不能将两套文件任意混装。

运行依赖包括设备已有的 Python（含 audioop）、audio_lifecycle、home_features、intern_chat、mp3stream、GStreamer 0.10/mixersink、LIPC、手动主页注册及配对配置。系统二进制、密钥、录音、歌曲和蓝牙抓包不公开。

## 音频路径

歌曲解码 → PCM 分块供给 → 持续 48 kHz 混音输出 → 原生 A2DP → AirPods。切歌更换输入，复用同一个输出进程；暂停用静音维持输出，避免原生蓝牙流挂起。首次连接或真实断链仍需建立蓝牙连接，“无重连”仅指正常已连接会话内切歌。

`BTplaybackData.playbackState` 是 Kindle 内部枚举：1 停止、2 暂停、3 播放。不能套用标准 AVRCP 的数值 1。持续输出期间上报 3，关闭输出才报 1；本地暂停保持 3。错误枚举曾导致双捏被解释成播放，以及音频状态不一致。

遥控监听使用 PTY 和持续 LIPC 事件订阅：单捏暂停/继续，双捏下一首。单曲循环时主动下一首仍可切歌；顺序/随机模式在歌曲结束后选下一首。暂停和停止本地曲目不应自动改成通话模式。

## 验收与限制

| 项目 | 证据 |
|---|---|
| 两文件与备份一致 | SHA256 见快照 README |
| 手动主页启动 | 服务启动、探针返回 KT3_OK |
| 0444 → 0445 | 同一 GStreamer 输出进程，时间推进 |
| 耳机实际声音 | 用户确认有声、无重连提示 |
| 单捏/双捏 | 此版本此前用户确认正常；本次恢复未重复完整手势回归 |
| 长时间、多次切歌 | 未通过完整稳定性验收，保留卡顿/无声历史 |
| 休眠、入盒、断网、冷启动 | 本次恢复未重新专项验证 |

进度条、进程存活、非静音 HCI 包均不能单独证明耳机发声。主机发包连续也不能排除无线侧问题。

## 排障结论及未合入项

设备约 500 MiB 总内存，采样时可回收缓存调整后余量约 194–195 MiB。没有证据表明几首歌曲完整载入内存；音频是分块读取。

但系统 audiomgrd 曾积累 35 个旧 mstream 映射。后续实验用 SIGINT 正常结束 gst-launch，六首切换映射保持 2，确认正常释放有用；用户仍无声，故泄漏不是全部根因。**本次按用户要求原样恢复旧版，该正常释放修复没有合入这份旧播放器。** 不应把后续实验修复描述为当前版本已有能力。

缓冲加大、原采样率双流保活和单流重开实验均未解决全部问题，不作为此次发布基线。错误使用全局 wirelessEnable 进行 Wi-Fi 对照曾联动蓝牙；该实验无效，不应重复用于隔离 Wi-Fi。

## 操作与回滚

保持 KUAL 手动打开，不添加开机启动；不改变原书库和触摸配置。设备当前两文件位于 `/opt/kt3-home/app/`，恢复源是 `/var/local/kt3-home-backup/continuous-state3/`。

有声但每曲重连的备选位于 `/var/local/kt3-home-backup/graceful-reconnect/`。回退需先确认没有 HFP 会话锁，停止手动服务、正常关闭混音流并等待退出，备份当前文件，再短暂将根文件系统改为可写，替换 server.py/stereo_player.py 后立即恢复只读并手动启动。不能直接覆盖正在运行的服务，也不要混用两个版本的文件。

保留既有一键退出/回滚到原系统入口。本仓库不提供跳过健康检查的自动刷入脚本；首次恢复连接后仍需实听验收。旧 main 保留用于历史追溯，新分支作为默认开发基线，不代表上述已知问题已根治。
